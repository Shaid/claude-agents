# A platform port's byte-order convention is not automatically uniform across every format it ships

**When it bites:** you've already confirmed one format's byte order for a
platform port (e.g. "this Amiga port's `.FOO` is big-endian, matching the
CPU's native order") and are about to assume a *sibling* format in the
same port shares that same convention without independently checking it —
especially when the sibling format also happens to match a *different*
already-solved port's own encoding (e.g. matches the DOS/x86 sibling port's
little-endian convention instead).

Confirmed on Eye of the Beholder II (Amiga, `crawl` project): this port's
`.VCN` tile data, `.CPS` bitmaps, and `ITEM.DAT`/`ITEMTYPE.DAT` stat tables
are all a consistent hybrid — EOB2's own container/mechanism wrapping
data encoded exactly like EOB1's *Amiga* port (big-endian palette words,
5-bitplane pixels). Given that pattern, `.VMP` (the wall-view mapping
table) would be expected to follow the same big-endian convention EOB1
Amiga's own `.VMP` already uses. It does not: reading `.VMP`'s leading
header word and tile-index words as **little-endian** produces a
self-consistent, plausible result (`330 + N*431`, matching EOB2 *DOS*'s
own entry-count formula exactly, and an ascending-then-mirrored index run);
reading the same bytes big-endian produces meaningless values (implausible
multiples of 256). So within one single Amiga port, `.VCN`/`.CPS`/
`ITEM.DAT` are big-endian (matching the CPU/EOB1-Amiga) while `.VMP` is
little-endian (matching the DOS sibling port instead) — a real,
non-uniform mix, not a mistake in either direction.

**Why this happens:** byte order in this era is usually a property of
*which team/tool wrote the data file*, not a hardware constraint the whole
port must obey — a table hand-authored or generated by a shared
cross-platform tool (or carried over unchanged from the DOS build's own
asset pipeline) can retain its source platform's endianness even inside an
otherwise-native-endian Amiga port, while a table the Amiga-specific
renderer needs to touch directly (palette words feeding hardware chip
registers, bitplane pixel data) gets authored/converted to match the CPU.

**The fix:** treat every format's byte order as its own independent
question, checked against real bytes (a plausible ascending/self-describing
value under one reading vs. nonsense under the other — the same technique
`endian-swap-needs-matching-field-width.md` uses), even after several
sibling formats in the same port have already converged on one convention.
A format-by-format table in the doc (see `docs/eotb2/amiga/data-structure.md`'s
summary table) makes this mix explicit rather than letting a false
"port-wide rule" creep into later work on the same corpus.

**Second confirmed instance, mixing a different axis the same way:**
Muramasa: The Demon Blade (Wii, `vanille`)'s `FMBS` sprite-model container
is a third sibling of a format already solved on two other platforms —
PS2's `FMBP` (little-endian, compact 0xA0 header) and PS3's own `FMBS`
(big-endian, a dedicated, differently-laid-out 0xE4 header). Being closer
in generation to PS3 and sharing its `FMBS` name, Wii's header would be
expected to reuse PS3's 0xE4 layout. It doesn't: Wii's header is
byte-position-identical to PS2 `FMBP`'s compact 0xA0 layout, but every
field is read big-endian rather than `FMBP`'s little-endian — i.e. Wii
independently combines PS2's *field-position* convention with PS3's
*byte-order* convention, matching neither sibling wholesale. Confirms the
principle generalizes past byte order alone: any confirmed-shared format
axis (byte order, field-position layout, section strides) is its own
independent question per sibling platform, and a third variant can
recombine two already-seen conventions in a way neither existing sibling
predicts. The mismatch was cheap to detect (the header's own `headerSize`
field value, `0xA0` vs `0xE4`, immediately discriminates which layout
applies — every file failed an `assert headerSize === 0xE4` on the first
parse attempt); the real cost was re-deriving Wii's own per-section byte
strides from scratch rather than inheriting either sibling's.
