# A per-resource subset alphabet defeats every whole-corpus text scan — search by statistical shape, not byte values

**When it bites:** hunting for a game's dialogue/script text format; a whole-disc ASCII/Shift-JIS/known-encoding scan finds nothing; a small-alphabet byte-value filter (e.g. "bytes under N") passes almost everything and discriminates nothing; individual candidate resources "look like" numeric tables rather than text when eyeballed.

Text does not have to use one game-wide character table. Confirmed on Valkyrie Profile (PSX, the exact format the fan community failed to crack for 15+ years): each text resource ships its own **subset font** — bundled in the same container as that resource's strings — holding only the glyphs that resource actually uses, laid out in **order of first use within that resource's own string table**. The consequence: byte `0x0d` is a space in one resource and a completely different glyph in the next, because every resource independently permutes the "alphabet." No single-alphabet assumption survives contact with this design: a whole-disc plaintext/Shift-JIS scan finds zero hits (confirmed: 0 matches across 552 million decompressed bytes on Disc 1, the only string found being an unrelated SDK debug message), and a fixed byte-value-range filter can't discriminate because it doesn't know *which* bytes are meaningful in *which* resource.

**The technique that works is permutation-invariant**: don't test byte values, test the *shape* of the byte-value distribution against natural language, using statistics indifferent to which symbol means what.
- Sort a window's symbol frequencies descending and compare the shape to English's (a handful of symbols dominate, then a long tail).
- Compute the index of coincidence (real language ≈ 0.065-0.07 including a common "space" symbol; a flat/random distribution over N symbols ≈ 1/N, an order of magnitude lower).
- Compute the gap distribution between consecutive occurrences of the single most frequent symbol (real prose's word-length distribution: mean ≈ 4-5, essentially never exceeding ~14-15) — a numeric/table record with a fixed stride produces an obviously different (constant or narrowly-clustered) gap distribution instead.

Run over fixed-size windows at a stride across the whole decompressed corpus, this isolates real text blocks directly, with no prior knowledge of the encoding.

**Recovering the actual decode key once candidates are found**: search the isolated candidates for one that happens to ship the **complete** reference alphabet in a known, deducible order — e.g. a resource whose string table opens with a literal sequential glyph chart (`0x01, 0x02, 0x03, ...`), which under the "glyphs are ordered by first use" rule means glyph `i` is exactly the `i`-th character of whatever fixed alphabet the game uses (ASCII, in this case). That resource's glyph *bitmaps* then become a byte-exact bitmap-to-character dictionary: match every other resource's subset-font glyph bitmaps against it byte-for-byte to resolve that resource's own byte-code-to-character table, independently, per resource. No cross-resource assumption is needed once this one reference exists.

**A structural invariant worth checking as corroboration, not as the primary evidence**: if the encoding really does follow "glyphs ordered by first use," scanning a resource's decoded string bytes and recording the order distinct values first appear should yield exactly `1, 2, 3, ...` (control/formatting codes excepted). This doesn't prove the format — a numeric table could coincidentally satisfy it too on a short sample — but a large corpus-wide near-100% hit rate for it is strong supporting evidence once the primary statistical/bitmap-matching evidence already carries the claim.

**A negative result under this trap can be exactly correct about the wrong object.** On this project, an early pass found a real, genuine 213-entry ascending offset table in a resource that looked exactly like a plausible font (right shape, right rough size) and tried rendering it as a glyph bitmap at several pixel widths — a real, honestly-executed test that legitimately found nothing, because that specific resource turned out to be an unrelated bytecode/script table, not a font at all. The "renders as noise" result was correct; the assumption that this particular resource was the font was wrong. When a structurally-plausible candidate for an encoding scheme renders/decodes to noise, don't conclude the *scheme* is wrong before checking whether the specific *candidate object* was actually the right one to test.
