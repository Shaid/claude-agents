# A resource directory can be XOR-encrypted — only loader-data tracing finds it, not structural scanning

**When it bites:** a structural/entropy scan (ascending-value-run scan, low-entropy-region scan, raw-magic-byte scan) across a whole container comes back completely empty for a directory/table of contents you have strong reason to believe exists (a huge single-file container with thousands of addressable sub-resources and no ISO9660-level directory tree).

Every structural scan assumes a real table will *look* structured — ascending values, low local entropy, a recognizable magic. A directory encrypted with even a trivial keystream defeats all of these at once, because it's indistinguishable from any other block of compressed/opaque data. Confirmed on Valkyrie Profile (PSX): `VALKYRIE.BIN` (a 635 MB single-file container holding 99.98% of the game, no on-disk directory tree) resisted three independent structural scans for a master directory — a blind ascending-`u32`-run scan of the boot executable's data section, a low-entropy-region scan of the container's first several MB, and a raw-magic-byte scan for an uncompressed resource header at a sector boundary. All three came back empty or with only false positives (hardware register tables, geometry data, a math ramp table), because the real directory — 5,120 slots, sitting at byte 0 of the container — is XOR-encrypted with a simple rolling keystream (`key ^= (key<<1)`, remixed per field). It looked like ordinary high-entropy compressed data to every scan.

It was found not by scanning at all, but by tracing the boot executable's own **data flow**, not its byte content: a hardcoded read-position constant (a fixed disc address, baked directly into the loader function as an immediate) is read unconditionally at boot, before any other file access. That constant *is* the directory's address, regardless of what the bytes at that address look like. The general move: when a directory/table search comes up empty across every structural signature you can think of, stop scanning bytes and start tracing the loader's control flow (Method §2, "find the reader") specifically for a literal, unconditional "read N bytes starting at fixed position P" early in boot — P is the directory's address whether or not its contents are encrypted, compressed, or otherwise opaque. Confirm by attempting a plausible cipher against the bytes at P (start with the simplest rolling-XOR-keystream family) and checking whether the decrypted result satisfies the domain's own structural invariants (valid BCD/date fields, in-range indices, etc.) — that's the actual verification, not visual inspection of the ciphertext.

**A related trap this creates**: a first disassembly pass concluded "the boot executable is too small/simple to contain the general resource manager" (true) and inferred from that "the addressing mechanism must live in an undisassembled overlay" (wrong, and expensive to chase — a follow-up slide-correlation to pin the hypothetical overlay's RAM base only produced an inconclusive plateau, costing real time before the encrypted-directory answer was found one instruction further down the very call chain already being traced). The real design was split: the small boot executable holds the loader, the decryptor, and the index→address resolver; the actual *table* lives in the encrypted on-disc bytes. A directory search that only inspects the executable's static data, or only inspects the data file's structure, will miss a split design like this — trace the *loader code* across both, not each file independently. And don't stop a promising disassembly trace one call short of where it's heading: the actual answer here was a single `jal` past where the trace had been read as "a fixed destination buffer."
