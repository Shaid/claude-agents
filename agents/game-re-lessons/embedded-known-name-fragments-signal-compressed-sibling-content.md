# Readable fragments naming an already-known sibling format/container inside an "unclassified" leaf mean it's compressed, not opaque

**When it bites:** a container walk's magic classifier leaves a sizeable bucket of leaves "unclassified", and before writing it off as opaque you find short readable ASCII runs in a few members that name things the project already knows — a sibling container's self-name, a confirmed magic/tag, a build-tool path, or a literal prefix of an already-decoded header.

That is the signature of a byte-oriented LZ compressor: first-occurring text and literals pass through mostly intact while match tokens around them look like noise. It is much stronger evidence than "high entropy" alone. Distinct from `decoded-random-looking-region-is-compressed-files.md` (a directory already points into the blob) and `undecoded-format-may-be-compressed-with-known-codec.md` (one resource type's implausible counts or periodic artifacts).

**Check / fix:** byte-dump a handful of members' *full* content (not just the 16–64 bytes most probes read) and scan for readable runs. If any name a confirmed project format — especially a literal prefix match of a known header — treat the bucket as compressed sibling content and escalate with the exact strings, their offsets, and the prefix match.

**Canonical example:** Drakengard (PS2, `flower`): a recursive walk of `IMAGE.BIN` left 662 leaves (81% of the archive's bytes) with magic `\0V3a`, correctly un-recursed. One leaf's first ~200 bytes showed `"tmp_pack.txt.bin"`, `"mmodel"`, `"CJFg"` (the project's skeleton magic), a build path `"convert\C_ALL\shapA"`, and the 8-byte run `66 70 6b 00 00 00 00 00` — exactly the confirmed `fpk` header's first 8 bytes. With that evidence `re-codebreaker` identified a custom 32-byte header around chained LZO1X blocks decompressing to known `fpk` trees, unlocking 3,368 character/prop packages a prior plan had miscounted as "297 total" (`tracker-prose-is-not-evidence.md`).
