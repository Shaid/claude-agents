# "Map script" files may be compiled native code bound to a fixed memory map

**When it bites:** a game ships per-level "script" or "overlay" files (map
behaviour, events, text dispatch) and you're about to reverse-engineer them
as a custom bytecode/VM format — hunting opcode tables, building an
interpreter port, searching for bytecode-level structure. The files may
instead be **compiled machine code** (8086/68k/etc.) generated by an
overlay compiler, position-*bound*: the code references the game's **fixed
memory addresses** directly (absolute segment:offset constants the overlay
loader/relocator expects), not offsets into a script buffer.

**The tell:** run a disassembler over the first hundred bytes before doing
anything structural — a bytecode-framing analysis of `MOV AX,0xF4A1;
MOV [0x134],AX; ... RET` would waste hours; capstone/r2 identifies it as
native code in seconds. Two corroborating signs: (1) the file has a tiny
header (a few u16s) with code-size + data-size fields and a constant entry
offset, exactly like a compiled overlay; (2) the code's immediate/memory
operands land on the game's known data addresses (values that also appear
in a shipped symbol/relocation table if one exists — see the MM.RSM
addendum in game-re-tooling/dos.md). When the code is bound to a fixed
memory map, "decoding the script" becomes a disassembly-against-memory-map
project (plus the game's loader/relocator), not a bytecode interpreter.

**Confirmed on:** Might and Magic I (DOS): the 55 `*.OVR` "map script"
overlays turned out to be compiled 8086 code (entry offset 242 into the
code segment; `MOV AX,0xC940` at entry writes the game's fixed far pointer;
references to 0xC973/0x3C3A...) with a data segment holding selection
tables and the map's text. The container (14-byte header, `code_sz`/
`data_sz`, 55/55 `14+code+data == file size`), the WALLPIX wall/lane
selection fields, and all 387 text strings were extracted without touching
the code; the script *semantics* remain a memory-map-bound disassembly
project (see crawl docs/mm1/dosega/data-structure.md).

**When the bytes right after the header aren't code — don't stop there.**
The "disassemble the first hundred bytes" tell can mislead if a small
function/export table (a pointer array, not instructions) sits between the
header and the real code — a first-100-bytes disassembly of that region
looks like garbage/data, tempting the conclusion "not native code after
all." A cheap, disassembler-free alternative that's robust to this: a
whole-file *word-level opcode-shape census* — for MIPS/EE, count exact hits
for `jr ra` (opcode `0x03E00008`), `addiu sp,sp,X` (top 16 bits ==
`0x27BD`), and `jal` (top 6 bits == `3`); analogous shape checks exist for
other ISAs. Thousands of hits densely spread through the file (not just
near the start), plus a literal byte-exact function prologue/epilogue idiom
(`addiu sp,sp,-N; sd ra,0(sp); ...; jr ra; addiu sp,sp,N`) found by scanning
for the densest 256-word window, is conclusive without needing a
disassembler at all. Confirmed on the PS3 "ZOE HD Collection" build's
`ZoE2/bin/*.bin` per-stage overlays (`zoe2anubis`/`ps3`): the first ~0xC0
bytes past the 16-byte header were a `{garbage_u32, in-file-address_u32}`
export/pointer table, not instructions; the real code density (4,000+
`jr ra`, 6,000+ `addiu sp,sp,X`, 20,000+ `jal` per file) and the textbook
prologue/epilogue pair only showed up ~1.1 MB into a 2.3 MB file. Retained,
non-stripped PS2 SDK debug strings (`libmpeg 2500`, `libipu 2500`,
`../../system/libscn/libscn.h`, `local_resource.cc`) independently
corroborated compiled code with linked library debug info. All 130 files in
the corpus shared one constant load-base header pair (base, base+0x10),
confirming the fixed-memory-map binding this file's title describes.
