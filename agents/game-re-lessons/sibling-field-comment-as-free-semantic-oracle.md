# A sibling field's own detailed comment can already prove an adjacent enum's documented direction wrong

**When it bites:** you're about to trust a documented enum/state-value
mapping (e.g. "state 3 = X, state 1 = Y") at face value — especially one
whose only apparent evidence is its own restatement in several files —
before wiring it into new code or a new investigation. Also check this
before believing a struct field's doc comment is self-consistent just
because nothing else contradicts it in the same paragraph.

An inverted (backwards) semantic label for a small enum can be wrong for a
long time and propagate everywhere, because every file that states it just
copies the same (wrong) direction from the first place it was written, and
nothing crashes: the field is still read and written consistently *within*
that wrong convention, so tests and gameplay both "work" — the bug is only
that the human-readable name attached to each numeric value is swapped, and
in a live simulation that consumes and mutates the field bidirectionally,
this can hide indefinitely.

Confirmed on War in Middle Earth (`middilgard`, Amiga): a 2-bit movement
state field was documented in five places (three TypeScript struct comments,
one browser-engine docblock, two markdown format-spec files) as `1 = camped,
3 = actively moving` — and the live engine (`MovementSystem.ts`,
`GameTimer.ts`, `Game.ts`) had the identical inverted convention baked into
real gating logic (simulate movement only when `moveState===3`; report
"resting" for `moveState===1`), all self-consistently wrong. The tell was
sitting one field down in the exact same struct: the `stamina` field's own,
more specific comment ("regenerated by 2 per tick **while resting (moveState
3)**; on reaching 0 the unit is forced into **moveState 3**") was already
correct — nobody had cross-checked it against the `moveState` field's own
comment two lines above, which said the opposite. A stamina-regen-rate
detail is a very specific, hard-to-fabricate claim; when a detail that
specific contradicts a nearby summary label, the summary is the one to
re-derive from source, not the detail.

**Fix:** when documenting or reviewing an enum/state field, scan sibling
fields in the same struct for any comment that names a *specific numeric
value* of that enum (a threshold, a trigger condition, a rate) — these are
cheap, already-written, independent oracles for the enum's direction, and
disagreement between two comments in the same file is a stronger and
cheaper signal than either comment's own confidence. If a fix is warranted,
audit every consumer that branches on the field's value (not just the
comment) before shipping — an inverted convention this pervasive is rarely
confined to one call site, and flipping only some of them regresses the
rest (see `producer-fix-inert-without-consumer-audit.md` for the general
"audit every consumer" discipline once a fix is identified).
